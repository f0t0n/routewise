# Implementation Plan: the binding is generated (R14), release 0.4.0

Spec: [SPEC.md](../SPEC.md), R14, Objective items 4 and 5, success criteria 2, 3 and 19 (approved 2026-11-18). Tasks: [todo.md](todo.md). Earlier plans: [done/](done/).

## Overview

`ROUTING-BINDING.md` becomes a generated file, rendered on every run from `templates/binding.md`, the shipped roles, the harness map, the rules spec's version and a new `[binding]` table in `routewise.toml`. A new or changed role reaches every project with the update; the person's only entries are five values in `routewise.toml`. An approval older than the shipped rules spec shows "approval pending" without failing anything. A binding written before 0.4.0 (no marker) stops the run with the fix in the message.

## Architecture decisions

- **`[binding]` is parsed in `lib/settings.py`,** like the other tables: types, one-line text, length, forbidden characters, ISO dates, an integer version. Errors are `SettingsError`, exit 2, naming the key and the fix.
- **A new module `lib/binding.py`** renders the file: the marker line, the approval line or "approval not recorded" or "approval pending", the fixed rows from the template, and one row per shipped role (`<name>` | `<tier>` at `<effort>`, with "approval pending" on `frontier` rows when pending). It reads the rules spec's version from its version line (`Version N, …`). Pure functions, unit-tested; `lib/install.py` only plans the write.
- **Marker and ownership:** `is_generated_binding(text)` checks the first line's prefix `<!-- generated by routewise from `. The installer plans the binding on every run when the file is absent or marked; an unmarked file raises the installer's error before anything is planned (S2), in install and `--check`; `--uninstall` removes a marked file and keeps an unmarked one with a note.
- **Role rows lose their hand-written notes** (R-A4, R-A5 hints) except what the template can say once for all roles; the rules spec is linked for the reasons. Kept small on purpose: the binding states choices, the rules spec explains them.
- **The rules version is read, not hard-coded,** so a rules spec bump marks approvals pending with no code change.
- **This repo migrates by hand** in the docs task: its values go into its own `routewise.toml`, its old binding is deleted, `make self` renders the new one, and `make check` covers it from then on.

## Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| routewise overwrites a binding the person wrote | High | Only a file whose first line carries the marker is rewritten or removed; unmarked stops the run; tests for both, and `auditor`. |
| A `[binding]` value breaks the Markdown table or ends the marker comment | Medium | One line, no control characters, `|` or `-->`, at most 200 characters; tests for each. |
| An update silently "approves" a new frontier role | High | routewise never writes `routewise.toml` after the first run; pending approval rendered and printed; test that an update with an old `approved_rules_version` renders pending. |
| Every project's first 0.4.0 run stops | Low (accepted) | The message carries the exact fix; the release notes repeat it; Task 5 tries it on a real 0.3.0 project. |
