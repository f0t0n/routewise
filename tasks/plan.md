# Implementation Plan: review roles load checklist skills, stand-ins for /ship (R8, R9), release 0.2.0

Spec: [SPEC.md](../SPEC.md), R8 and R9, success criteria 13 and 14 (approved 2026-11-17), and rules spec version 3. Tasks: [todo.md](todo.md). Earlier plans: [done/](done/).

## Overview

routewise keeps owning how a review runs (tier, effort, read-only tools, return shape); a skill named in the role supplies what to check. `reviewer` and `auditor` get a `skills` frontmatter key (agent-skills by default), a project can change it in `routewise.toml` `[skills]`, and the role bodies say how a skill and the body work together. R9 lets a project render the same roles under the plugin's persona names (`[stand_ins]`), so agent-skills' `/ship` runs the read-only roles.

## Architecture decisions

- **`skills` lives in the neutral role file, overrides in `[skills]`**, as tiers live in `harness.toml` with overrides in `[tiers]`: projects installed before 0.2.0 get the defaults with no settings change.
- **One name pattern for skills, shared by `roles.py` and `settings.py`** (like `MODEL`): one or two parts of `[a-z0-9-]`, joined by one `:`; at most 32 names. Nothing else can reach a frontmatter line.
- **Rendering per harness, like `tools`:** Claude Code gets `skills: a, b` (comma-separated, as `tools`), Antigravity `skills: [a, b]` (YAML list, as its `tools`). Task 1 checks the two-skill form live on Claude Code; one-skill and Antigravity's forms were probed on 2026-11-17.
- **Unknown role in `[skills]` or `[stand_ins]` is checked in `install.py`**, where the roles are known; `settings.py` checks types and names only.
- **Stand-in marker (needs approval, see Open questions):** a stand-in file carries `# generated by routewise from roles/reviewer.md as code-reviewer.md; edit that file and re-run …`. `is_generated` accepts the file when the name after `as` equals its file name, else (no `as`) when the source's name does, as now. Role files keep today's marker byte for byte, so nothing installed before changes. An older routewise reads a stand-in as a user's file and never deletes it, the safe direction.
- **Fragment placeholder `{{stand_ins}}`:** one line when stand-ins are set, nothing otherwise, so projects without R9 get an unchanged block apart from R8's lines.
- **No plugin detection:** the installer reads nothing outside the project (S1); the role's `Checklist:` line and the fragment rule surface a missing skill at run time.

## Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Claude Code reads a two-skill `skills:` line in another form than `a, b` | Med | Live probe in Task 1 before the format is fixed; fall back to the YAML list form |
| Marker change breaks detection of existing generated files | High | Role files keep the exact old marker; tests for old marker, stand-in marker, renamed copy of each |
| A skill name or stand-in name injects frontmatter or a path | High | Strict patterns, tested with a line break, `/`, `..`, spaces, upper case; `auditor` in Review |
| A stand-in name collides with a role or a user's agent | Med | Refused: name equal to a role; a non-generated file of that name stops the run (S3) |
| Skill text steers the role against the body | Med | "The body wins" rule; no write tools; `auditor` review of the body text |
| A session picks `agent-skills:code-reviewer` despite the stand-in | Med | Fragment line (Task 7); live `/ship` run in Verify shows which ran |
| Role bodies grow and cost context on every call | Low | Only the R8 rules are added; the checklist stays in the skill |
