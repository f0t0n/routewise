`ROUTING-BINDING.md` now keeps itself up to date. It is rendered on every run from the shipped roles and a new `[binding]` table in `routewise.toml`, so a new role (like 0.3.0's `judge`) or a changed tier reaches every project with the update, and you never edit the binding by hand again. Updating to this version needs one step, once.

## New

- **The binding is generated.** Its first line is a marker (`<!-- generated by routewise from … -->`), and it is rewritten on each `routewise/install`, like the agent files. It lists every shipped role with its tier and effort, the tier-to-model map with your `[tiers]` overrides, and your approval. `--check` reports it as drift when it is out of date; a hand edit is drift too and is overwritten by the next install.
- **Your entries move to `routewise.toml`,** in a `[binding]` table:

  ```toml
  [binding]
  approved_by = "Ann (maintainer)"   # who approved the routing
  approved_on = "2026-11-18"         # when (a TOML date works too)
  approved_rules_version = 4         # the rules spec version the person approved
  assistant_pins = "not an assistant project"
  review_from = "2026-12-02"         # first miss-log review, then monthly
  ```

  Values are checked so they cannot break the binding: one line, at most 200 characters, no `|`, `<`, `-->` or `{{`, real dates.
- **Approval stays a person's act.** The binding says "Approved by … for rules spec version N", or "approval not recorded", or, when a newer rules spec ships, "approval pending" with each role on the `frontier` tier marked; the install prints the pending line too. A pending approval never fails a run or `--check`. routewise never writes `routewise.toml` after the first run, so no update can approve anything: you change `approved_rules_version` (or your agent does, on your word). A version without `approved_by` counts as not recorded.

## Changed

- `--uninstall` now removes the generated binding; `routewise.toml` (with your `[binding]`) and the miss log stay, so a re-install renders the same file.
- The binding's "Installed <date>" line is gone (git history has it), and its role rows give tier and effort only; the shipped rules spec, which the binding links, explains them.
- A `ROUTING-BINDING.md` that is a symlink, a folder or not readable as text is never replaced: the install stops with a message.

## Update

From the project root (the old folder is replaced only after the download succeeded):

```sh
v=0.4.0
mkdir routewise.new && curl -fsSL "https://github.com/f0t0n/routewise/archive/refs/tags/v$v.tar.gz" | tar -xz --strip-components=1 -C routewise.new && rm -rf routewise && mv routewise.new routewise && routewise/install
```

**The first run stops, once.** Your current `ROUTING-BINDING.md` was filled in by hand, so routewise will not overwrite it: the install exits with code 2, writes nothing, and says what to do:

1. Add a `[binding]` table to `routewise.toml` (example above) and move over the approver, the assistant pins and the miss-log review date from the old binding.
2. For `approved_rules_version`, **ask the person which rules spec version they approved.** Neither the release a project ran nor text in the old binding is proof: 0.3.0 wrote "approved here by adopting rules spec version 4" into every binding on its own. If they do not say, leave it out; the binding then says "approval not recorded" until they approve. This release ships rules spec version 4, unchanged since 0.3.0.
3. Delete `ROUTING-BINDING.md` and run `routewise/install` again. It writes the new, generated binding.

Commit `routewise/`, `routewise.toml` and the new `ROUTING-BINDING.md`. The agent files and the delegation block do not change in this release, so no new session is needed.
